# CVA6 scalar core

The `CVA6` implementation of the NPU scalar core: a CVA6 RISC-V core that runs
firmware from DDR and drives the matrix core through memory-mapped job
registers. It is selected with `SCALAR_IMPL = "CVA6"` on the `scalar_core`
wrapper and has the same port list as the default `CUSTOM` implementation in
`../custom/`. Plan: [docs/plans/2026-1112-003-cva6-scalar-core.md](../../../../../../docs/plans/2026-1112-003-cva6-scalar-core.md).

Status: simulated. `make -C src/test sim-cva6` (Verilator) runs the seven
ISA test programs, translated to RISC-V by
`src/test/vectors/risc_v_npu/isa_to_rv.py`, and every final memory image
equals `src/test/model/isa_sim.py`. Results: `exp/scalar_core_compare/`.
Programs generated by the back end (`src/vendors/risc_v_npu/`) have not run
on this RTL yet, and nothing has been synthesized or run on the board.

## Upstream pin and patch policy

- `upstream/` is pinned to the `v5.3.0` tag and never modified. Customization
  goes only through CVA6's configuration struct (`cva6_config.sv`), which
  `scalar_core_cva6` passes as
  `.CVA6Cfg(build_config_pkg::build_config(cva6_npu_config_pkg::cva6_cfg))`.
- If a source change ever becomes unavoidable it lives in `patches/` next to
  this file, is applied at build time, and is listed here. There are none.
- Nested submodules needed: `core/cvfpu`, `core/cache_subsystem/hpdcache` and,
  inside cvfpu, `src/fpu_div_sqrt_mvp` (listed by upstream `core/Flist.cva6`).
  Not needed: `verif/core-v-verif`, `verif/sim/dv`, the `corev_apu/*` ones and
  the documentation ones. The pulp `axi`, `common_cells`, `fpga-support` and
  `tech_cells_generic` libraries are vendored in the CVA6 tree under
  `vendor/pulp-platform/`.

  ```bash
  git submodule update --init src/hw/rtl/npu_accelerator/scalar_core/cva6/upstream
  cd src/hw/rtl/npu_accelerator/scalar_core/cva6/upstream
  git submodule update --init core/cvfpu core/cache_subsystem/hpdcache
  git -C core/cvfpu submodule update --init src/fpu_div_sqrt_mvp
  ```

  On Windows the last step exceeds MAX_PATH inside a worktree (the nested git
  directory path is about 200 characters); pass `git -c core.longpaths=true`
  to that step and to a later `git status` of the superproject, or set
  `core.longpaths` in your own git configuration.

## Configuration: deltas from `cv32a60x`

`cva6_config.sv` starts from upstream `core/include/cv32a60x_config_pkg.sv`
(v5.3.0) field by field. Fields that differ:

| Field | `cv32a60x` | Ours | Why |
|---|---|---|---|
| `CachedRegionAddrBase` / `Length` | `0x8000_0000` / 1 GiB | `0x0` / 512 MiB | the PYNQ-Z1 DDR is at 0; otherwise DDR would be uncached and the 2 KiB I$ / D$ unused |
| `NrNonIdempotentRules`, base / length | 0 | 1: `0x4000_0000` / 4 KiB | DOORBELL, FENCE and DONE have side effects; CVA6 must not speculate or repeat them |
| `NrExecuteRegionRules`, base / length | 0 (everything executable) | 1: DDR only | a jump into MMIO or unmapped space traps instead of executing garbage |
| `CvxifEn` | 1 | 0 | no custom instructions; the matrix core is driven through MMIO |
| `CVA6ConfigRvfiTrace` (package constant) | 1 | removed | not referenced by `cva6.sv`; it only belongs to the upstream package |

Kept as `cv32a60x`, including `AxiAddrWidth = 64`: the plan asked to try 32.
No upstream assertion forbids it, but every upstream configuration uses 64,
and the HPDcache uses `AxiAddrWidth` as its memory address width while its
physical address is `PLEN = 34` bits for `XLEN = 32`, so with 32 it would
silently truncate addresses in a combination upstream does not test.
`scalar_core_cva6` instead drops bits [63:32] after the address decode, which
only sends addresses below 512 MiB to `m_axi`. Area knobs left for the P2
synthesis gate: `RVB`, `RVZCB` (1 → 0), `BHTEntries`.

## Address map

| Range | Target | Notes |
|---|---|---|
| `0x0000_0000` - `0x1FFF_FFFF` | DDR via `m_axi` | cached (write-through D$), executable |
| `0x4000_0000` - `0x4000_0FFF` | `cva6_npu_mmio` | uncached, non-idempotent; never visible on `m_axi` |
| anything else | `axi_err_slv` | DECERR |

The MMIO base and the cached DDR size are open decision 1 of the plan; both
are constants at the top of `cva6_config.sv` and used by the decode in
`scalar_core_cva6.sv`.

## MMIO registers

32-bit registers on the 64-bit bus (lane selected by address bit 2; reads
return the register in both lanes). Single-beat accesses only: a burst, an
unknown offset or a write to a read-only register is answered SLVERR.
Error codes are those of `src/vendors/npu_pynq/spec/abi.py` and the CUSTOM
core.

| Offset | Name | Access | Meaning |
|---|---|---|---|
| 0x00 | `SHAPE_MN` | RW | M `[15:0]`, N `[31:16]` |
| 0x04 | `SHAPE_K` | RW | K `[15:0]` |
| 0x08 | `ADDR_A` | RW | A operand address (8-byte aligned) |
| 0x0C | `ADDR_B` | RW | B operand address (8-byte aligned) |
| 0x10 | `ADDR_C` | RW | C result address (8-byte aligned) |
| 0x14 | `DOORBELL` | W | latch one GEMM job from the registers above into the one-entry queue; the write response is held while the queue is still full |
| 0x18 | `STATUS` | R | `[0]` busy, `[1]` error (sticky), `[15:8]` error code, `[23:16]` jobs outstanding (queued or issued, not written back) |
| 0x1C | `FENCE` | R | as `STATUS`, answered only once every issued job has been written back (or a fault is latched) |
| 0x20 | `DONE` | W | `[7:0]` error code, 0 = success; ends the program |
| 0x24 | `DATA_BASE` | R | `data_base` from the CSR (the job descriptor table) |
| 0x28 | `PROG_LEN` | R | `prog_len` from the CSR |

`DATA_BASE` and `PROG_LEN` are additions to the plan's table: the firmware has
no other way to read the CSR arguments.

Job issue mirrors the CUSTOM core's EX stage: `ctl_start` and `ctl_m/n/k` come
straight from flip-flops; a job issues when `ctl_accept`, the DMA's load and
store sides are ready, no fault is latched and the two-cycle cooldown after
the previous issue has expired; `m*k`, `k*n` bytes and `m*n` words are computed
when the job is latched. A shape outside `1..ROWS x 1..COLUMNS x 1..MAX_K`
latches `ERR_BAD_SHAPE` (0x11), a misaligned address `ERR_MISALIGNED` (0x12);
neither issues. Faults (those two, a matrix core error, DMA read 0x13 / write
0x14) latch the first code, drop the queued job and every later DOORBELL
(answered OKAY so the firmware does not trap), and end the program.

## Start, done and clock

- CVA6 is held in reset until an admitted `isa_start`; `boot_addr_i` =
  `prog_addr`, `hart_id_i` = 0, interrupts and debug tied low, CV-X-IF tied
  off.
- A DONE write or a latched fault ends the program: new CVA6 AR / AW requests
  are held back, the ones in flight complete, CVA6 goes back into reset, the
  DMA drains every issued job, then `isa_done` (code 0) or `isa_error` with
  the code. A latched fault takes precedence over the DONE code.
- `isa_running` = firmware running; `isa_busy` = not idle or jobs not drained;
  `isa_cycles` counts from start to done; `isa_jobs` = jobs written back.
- Open decision (plan 9.2): `isa_instructions` counts NPU jobs issued, not
  retired CPU instructions; `isa_pc` reports the boot address, as CVA6 exposes
  no PC outside its RVFI trace.
- One clock domain (100 MHz) for now. If synthesis misses it, the plan's
  fallback is a slower CVA6 domain with the CDC at the MMIO and AXI boundary.

## AXI topology

```
cva6 --> stop gate --> axi_demux --0--> axi_mux --> axi_id_serialize --> m_axi (32-bit, no ID)
                           |--1--> cva6_npu_mmio         ^
                           `--2--> axi_err_slv           |
                                  cva6_dma (ID 0) -------'
```

The plan put `axi_id_serialize` on the CVA6 path before the mux. It sits after
the mux instead, so the master port carries a constant ID and the ID-less
`m_axi` needs no response-ID bookkeeping of its own; the serializer keeps the
slave-side IDs and the in-order slave returns responses in request order.

## Building

The default flow (`make -C src/test lint sim`) does not need the submodule
and does not read this folder's CVA6-only files. With the submodule:

```bash
make -C src/test lint-cva6     # Verilator lint, scalar_core with SCALAR_IMPL="CVA6"
```

which runs

```bash
verilator --lint-only -Wall -Wno-DECLFILENAME --timescale 1ns/1ps \
  --top-module scalar_core -GSCALAR_IMPL='"CVA6"' \
  src/hw/rtl/npu_accelerator/scalar_core/cva6/waiver.vlt \
  -F src/hw/rtl/npu_accelerator/scalar_core/cva6/cva6.f <default RTL list>
```

`cva6.f` adds only what the default RTL list leaves out and defines
`NPU_SCALAR_CVA6`, without which the wrapper refuses `SCALAR_IMPL = "CVA6"`.
iverilog cannot compile CVA6 (type parameters, struct packages).
`build_overlay.tcl` does not read `cva6.f` yet.

## Known limits and what is unverified

Verified here: Verilator 5.050 `--lint-only -Wall` of `scalar_core` with
`SCALAR_IMPL = "CVA6"` (CVA6 v5.3.0 with this configuration, the pulp AXI
blocks and our files elaborate; clean with `waiver.vlt`), and
`tb_cva6_npu_mmio` under iverilog.

Not verified:

- Simulated by `tb_scalar_core_cva6` (Verilator): boot from `prog_addr`,
  MMIO job issue, DONE and the stop / reset sequence, the demux / mux /
  serializer with the DMA, and the final memory image against `isa_sim.py`.
  Still unverified: the D$ / DDR data path (the test programs use registers
  only), DECERR for unmapped addresses, compressed (RVC) code, the trap
  path, and programs generated by `LowerToRiscv`.
- No synthesis (area, Fmax at 100 MHz on the XC7Z020) and no board run.
- A program that never writes DONE runs until reset; there is no timeout.
- As in the CUSTOM core, a matrix core fault that leaves a job unwritten keeps
  `isa_busy` high until reset.
